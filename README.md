# agent-gate-catalog

**For English readers:** This repository publishes the operating rules of a single-operator AI agent environment: the gates that were moved from the human to the agent, the accident that produced each gate, and the measurement that shows whether the gate still fires. Most rules here have a firing path (a cron entry, a git hook, or a session-start step) and a source file; the ones without one are labeled as such (see §1, item 4). The metrics section reports numbers measured in that environment, including the ones that came out badly. The body of this README is in Japanese.

---

## 1. 何が起きて、何を置いたか

**2026-07-26 — 10分ごとの収集ジョブが284回連続で失敗し、48時間気づかなかった。**
定期実行に登録し、登録一覧の出力を貼って完了と報告していた。実行時の作業ディレクトリの指定が無く、依存の解決に失敗し続けていた。貼った実出力は「設置した」を証明しており、「成功した」は証明していなかった。
→ **置いたもの**: 全ジョブを wrapper で包み、実行のたびに `.ok` / `.fail` を打刻する。別のジョブが毎時「直近の発火が成功しているか」を判定する。
→ **測った結果**: 32行中30本を wrap（残り2件は `@reboot` と `&&` 連鎖で構造上変換できないと明記した）。監視漏れ0・孤児0。

**2026-07-27 — 毎メッセージ注入していた手順の遵守率が 0/24 だった。**
手順を全メッセージに機械注入する hook を結線し、発火ログで稼働を確認していた。実際の応答で手順が守られた回数は24回中0回。発火ログは「届いたか」の証拠であって、「従ったか」の証拠にはならない。
→ **置いたもの**: 結線を「注入 / 発火証明 / 遵守観測」の3層に分け、遵守観測を別のジョブが数える。
→ **測った結果**: 別セッションが合格を出した成果物の率 **12.0%（7/59件）**（2026-08-07T05:50:02+09:00 生成の版）。下限として置いた50%を割っている。

**2026-07-06 — 人に質問を投げると、作業を止めて相手にボールを渡せる。**
これが、詰まったときに最も安い逃げ道として機能していた。
→ **置いたもの**: 人への問いを2種類に機械分類する。不可逆・外向き・お金に触れるものは「止まる質問」で、明示回答が無い限り進まない。それ以外は「止まらない質問」で、期限が来たらデフォルト案で自動確定して進む。分類は宣言したアクションから機械的に導出し、判定不能は止まる側に倒す。
→ **測った結果**: 拒否猶予が与えられた16件のうち11件が期限で自動確定（**68.8%**）。期限後に覆した記録は **0/11**。

**2026-07-21 — 「毎ターン自動注入される」と自称していたリマインダが、15日間どこからも読まれていなかった。**
→ **置いたもの**: 無い。ファイルは今も存在するが、発火経路が無い。参照しているのは結線状態を検査する側だけで、実行経路からは呼ばれていない。
→ **測った結果**: 無い。この項目は「未結線」と記録されたまま台帳に載っている。

4件のうち3件は結線と実測まで到達し、1件は結線が無いまま台帳に残っている。

## 2. このリポジトリが配るもの

3つある。

1. **人間が持っていた判断のゲートを、AI 側へ移した移し方のカタログ** — skill 13本。設計の前に全体図を描かせる型、実画面を初見の人の目で歩く型、実装と検収を別の人格に分ける型など
2. **移した先で、そのゲートが効いているかを測る計器** — 制度文書19件＋型のみ2件と、その実測値（§3）
3. **移らなかった残余の席** — 選好の定義権と引き受けは人間に残す。その席の設計が「止まる質問」と「裁定パッケージ」で、**外向き・不可逆・お金の3つだけを人間ゲートにして、境界の内側は AI が自律で進む**

参照モデルの `tikalk/adlc-team-skills`（チーム向けに skills を配布する公開リポジトリ・2026-08-06 時点の表示値で118★）が「チームの知識を AI に渡す」なら、こちらは「**ゲートを AI に移す移し方と、移らない残余の席**」を扱う。

## 3. 測った数字

すべて単一運用者の1環境の数字で、採取時刻つきで載せる。**都合の悪い側に出たものも落としていない。**

表を読むための用語2つ。**セッション** = この環境で並走している複数のエージェントの作業単位（同時に数本が別々の案件を進める）。**台帳** = そのセッションどうしが、互いの成果物・引き受け・停止・人への問いを1行ずつ追記していく共有ファイルで、相互監査の記録はここに残る。

| 指標 | 値 | 採取 |
|---|---|---|
| 拒否猶予が与えられた問いのデフォルト自動確定率 | **68.8%（11/16件）** | 2026-08-05 の週次記録 |
| 期限後に人が覆した記録 | **0 / 11件** | 2026-08-06・拒否権ログを直接 grep（週次 JSON には override のキーが無い） |
| 別セッションが合格を出した成果物の率 | **12.0%（7/59件）** | FINDINGS 生成 2026-08-07T05:50:02+09:00 |
| 台帳に記録した稼働セッションの率 | 50%（2/4件） | 同上 |
| 止まる質問への応答 | 中央値 1.0日 / 最大 11.6日（n=8） | 2026-08-05 の週次記録 |
| 掲示の最古の未読 | 20.2日 | 2026-08-07T05:58:34+09:00 |

**分母の注記（重要）**: 世界標準の override rate の分母は「人がレビューした提案の数」。上の `0 / 11` の分母は「**レビューされずに期限で自動確定した件数**」で、rubber-stamp 側の量にあたる。この数字が言えるのは「拒否猶予が与えられた11件について、期限後に覆した記録が1件も無い」までで、「人がレビューした上で0件しか覆さなかった」ではない。

**この数字の制約**:

- **履歴は1週分しかない**。前週の記録が無く、集計器自身が「2週連続の判定が成立しない」と出力する。時系列で改善したという主張はできない
- 週次記録（2026-08-05）と再採取（2026-08-07）で値が動く。どの時点の数字かを添えないと比較できない
- 集計器がデータ異常を1件報告している（同一IDが open と resolved の両方に存在）。主要な数字への影響は無く、参考値の45.8%（11/24）が47.8%（11/23）に動く範囲にとどまる

## 4. 対訳表（抜粋）

ここにある型のほとんどは、世界に既に名前がある。**既知の概念のカタログ実装として出す**方針で、英語名を併記する。**公開する34項目**の全体は `docs/translation-map.md`（属地・案件固有のものは公開版から落としてある）。

### 既存名があるもの（抜粋）

| ここでの名前 | 世界標準の名前 |
|---|---|
| persona-walk | Cognitive walkthrough（Lewis, Polson, Wharton, Rieman 1990・CHI） |
| franchise-kaizen | Yokoten（横展開・Toyota）＋ pilot → rollout |
| toryo（棟梁体制） | Orchestrator-worker pattern ＋ Theory of Constraints（制約を遊ばせない） |
| map-first | Architecture Decision Record（Nygard 2011） |
| 自己検収の禁止 | Four-eyes principle / maker-checker / Segregation of Duties |
| 完了の定義＝検証コマンドと実出力 | Definition of Done ＋ audit evidence |
| 止まる質問 / 止まらない質問 | HITL approval gate ＋ lazy consensus（ASF）＋ irreversibility-based gating |
| 監督の質の実測 | Override rate / rubber-stamp rate |

### 既存名が見つからなかったもの（3件）

検索で同じ運用単位が見つからず、独立した検収者の承認を経て「新レール候補」として出す。**最も近い既存研究を先に名指しし、差分を書く。**

**crosswatch（並走セッションの相互監査）**
最も近いのは **Trust Without Trusting: A Recomputable Trust Protocol for Autonomous Agents**（arXiv:2605.06738）で、"a consortium of co-equal, mutually distrusting peers under a shared charter" という中核記述と語彙が重なる。差分は2点。

1. **検証の対象**: あちらは「公開済みの受入規則が宣言どおり適用されたか」を再計算で検証する。crosswatch が検証するのは**成果物の中身の質**で、別セッションが証拠ポインタつきの verdict を書くまで閉じない
2. **人間の席の有無**: あちらの構成に人間は登場しない。crosswatch には「**人に投げる必要のない問いを人に投げていないか**」を他セッションが指摘する条件があり、これは人間の帯域を守るための条件なので、人が居ない構成には対応物が無い

他に検討した近縁: CHAP（arXiv:2606.09751・全文で確認したところ review は必須ではない composable profile で、レビュー主体は人）／Deliberative Curation（arXiv:2606.00007・評判重み付き投票で知識ベースへの投稿を裁く。シミュレーション段階）／blackboard architecture・ledger-state stigmergy（台帳経由の間接協調は既存名がある）。

**この設計は、2026年の実務側の推奨とは逆を向いている。** 「peer どうしを協働させるなら arbiter（調停役）を残せ」「open mesh の peer-to-peer は本番で問題が多い」が現在の推奨で、crosswatch は arbiter を置かずに同格のセッションどうしの相互義務だけで回す。採用する場合は、この点を承知した上で判断してほしい。

**wiring_check（制度文書と現物の自動突合）**
散文で書かれた運用規範から機械検査できる主張だけを抽出し、`crontab` の実体・hook・ファイルの実在と突き合わせる。近縁は ARPaCCino（arXiv:2507.10584・自然文ポリシー → Rego → **IaC** を検査）と PROPARAG（arXiv:2605.07515・自然文の方針書を統制標準に照らす。**突合の相手も文書**）、doctest（文書に埋め込まれた実行可能例を検証）。実ホストを走査する側（OpenSCAP / CIS Benchmark）は成熟しているが、**入力は走査器のための機械可読プロファイル**で散文ではない。散文抽出側と実ホスト走査側の交差は見つからなかった。

**toi（問いの正本）**
事業が詰まったときに通す問いのカタログ。**問いを追加するには、その問いが過去に判断を変えた実績（出典）が要る**。回答は一次資料に接地した形でファイルに書き、決定論スクリプトが形式と接地を検査して通らない限り未回答として扱う。近縁の policy-enforced generation は**生成の出口に置く出力フィルタ**で、規則違反を拒否する。toi は問い（計器）の側に掲載資格を課す点と、拒否の基準が規則違反ではなく**一次資料を開かずに書いた浅さ**である点で外れる。

## 5. インストール

**plugin marketplace 経由（推奨）**

```
/plugin marketplace add HikariMush/agent-gate-catalog
/plugin install agent-gates@agent-gate-catalog
```

**skills CLI 経由**

```
npx skills add HikariMush/agent-gate-catalog -a claude-code -g
```

2つの経路の違いは1点。**hook（発火の結線）を同梱して配れるのは plugin 経路だけ**で、skills CLI 経由では SKILL.md とその同梱ファイルが入る（hook の結線は入らない）。この配布物の内容は「制度と、その制度を発火させる結線」の対なので、結線ごと入れる場合は plugin 経路を使う。skills CLI 経由は Claude Code 以外のエージェントにも入る（75種以上）。

リポジトリは両経路で成立するように、**プラグイン配下（`plugins/agent-gates/`）を単一ソース**とし、リポジトリ直下の `skills/` と `docs/` はその複製として置いてある。skill から制度文書への参照は `../../docs/institutions/…` の相対パスで書いてあるので、**どちらのツリーからでも解決する**。

導入後の最小の確かめ方: `/kansa` を起動し、冒頭に示される正本（[`docs/institutions/adversarial-audit.md`](docs/institutions/adversarial-audit.md)。skill からは2階層上の相対パスで指している）が導入先で開けることを確認する。plugin 経路ならプラグイン配下の `docs/` が、skills CLI 経由ならリポジトリ直下の `docs/` が参照先になる。

## 6. 制約と、書き方について

- ここにある数字は**単一運用者の1環境の実測**で、一般化された性能ではない。履歴は1週分しかない
- 制度の一部は**未結線のまま台帳に載っている**（§1 の4件目）。全部が動いている状態を配ってはいない
- この README の文は「**観測事実（日付・数字・実出力）／仕組みの記述／手順**」の3類だけで書いてある。訴求の文を置かない方針で、検出器（`copy_lint.py`）を通している
