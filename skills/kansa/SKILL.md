# kansa — 敵対監査と検収

> **この手順は自前の台帳・検査スクリプトを前提とする。** 同梱していないので、無い場合は同じ項目を手動で確認する（何を確認すべきかは各手順に書いてある）。

対訳: **adversarial review / red team review ＋ fresh-eyes review**。正本 = `../../docs/institutions/adversarial-audit.md`（**読まずに監査を始めない**）。

## 手順

1. 対象を特定して層を選ぶ
   - 完了報告の検証 → **層1**（検証コマンドとその実出力の実在確認。無ければ未完了と判定）
   - 成果物の検収 → **層2**（diff 実見 → テスト実出力 → 実データ/実機照合の3点。自己検収は禁止）
   - 前提・計画・判断の監査 → **層3**（新鮮な目の敵対監査）
   - 人間への裁定依頼の組成 → **層4**（裁定パッケージ5点）
2. 層3は**設計に関与していない別の人格**に発注する。渡すのは対象のファイルパスだけで、**結論と経緯は渡さない**（渡した瞬間に同じ穴に落ちる）
3. 出力の形
   - 層1/層2 → 証拠つきの合否（合＝実出力を引用／否＝欠けている証拠を列挙）。感想を書かない
   - 層3 → 必須スイープを全部実施し、実施痕を報告に含める。指摘は「想定 / なぜ浅いか / 壊れ方 / 最小検証手」＋**証拠**（引用 or 実出力）。証拠のない指摘は「所感」欄に隔離する。件数のノルマは置かない（水増しの禁止）
4. 結果を対象の正本に書き戻し、最重大の1〜3件を検証タスクとしてキューに積む。読んで終わりにしない
5. 新しい事故の形を見つけたら正本に追記する

## 発注の記録（記憶に依存させない）

監査を発注したら、その場で台帳に open する。**台帳に無い発注は存在しない扱い**。結果が返ったら outcome（findings / no_findings / aborted）とともに閉じる。**監査が死んだら aborted で閉じて再発注する**（成果物を先へ進めない）。

## 合格を出す前の検問（fail-closed）

層1/層2で「合格」と言う前に、台帳の検証コマンドを実行して実出力を報告に貼る。**非0で終了したら合格と呼んではいけない**（未発注・保留中・期限超過・中断・自己検収のいずれか）。特に **監査者と発注者が同一なら必ず False** になる。実装した本人が自分の成果物に合格を出せない規律を、文章ではなくコマンドで担保する。

「監査中」「監査待ち」と書くのは可。**未監査を「合格」と呼ぶことだけを禁止する**。

## 禁止

- 実装した本人（同一セッション・同一の人格）が自分の成果物に合格を出すこと
- 「テストが通ったはず」「反映されたはず」等、実出力のない合格判定
- 監査の省略を速度の理由で提案すること
- 証拠（引用・実出力）のない指摘を裁定やキュー起案の入力に使うこと
