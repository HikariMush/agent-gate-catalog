# map-first — 全体図を描いてから始める

対訳: **Architecture Decision Record（Nygard 2011）／ design doc ／ RFC 文化**。目的は**解決策への直行を禁止する**こと。手持ちの型を1つ、構造化なしに当てて走り出す事故を止める。

起源となった失敗: 教育設計で、構造化せずに手持ちの型（クイズ化）を当てて全却下された。手戻りの原因は実装の速度ではなく、**設計が割れないまま実装に入ったこと**にある。

## 手順（この順で・飛ばさない）

### step1. 問題の構造化

- **目標**: 何が達成されたら終わりか。**何を見れば達成と判定できるか**まで書く（文章だけの to-be は禁止）
- **要件の保存**: 依頼者の要件を番号付き（R1…）で `REQUIREMENTS.md` に保存してから設計に入る。会話で増減したら**先にファイルを更新**する。**要件を落とす判断は依頼者の明示合意なしにしない**
- **制約**: 破れない条件を列挙する（時間・人・人間ゲート＝外向き/不可逆/お金・恒久ルール）
- **現状**: **実測した事実のみ**。推測には「（推測）」と印を付ける

該当する設計では次の3つも埋める。

**(A) 制度・ルール・定期ジョブの新設 → 4点の所在宣言**
①**結線** = 何が発火させるか（定期実行 / hook / ワーカーが読むファイル / セッション開始時の手順）②**正本** = どの文書が真か ③**実出力** = 何を見れば動いたと分かるか ④**監査** = 誰がいつ不合格を付けられるか。1つでも書けなければ「未結線」と明記してから進む。**設置の実出力 ≠ 成功の実出力**。

**(B) 画面の設計 → 視線動線まで構造化する**
各工程で見る情報を列挙し、その工程ブロックの視線範囲内に同梱できるかを書く。**参照のためのスクロール往復を設計で作らない**。

**(C) セキュリティ影響 → 3問に1行ずつ答える。書けない設計は実装に進めない**
1. **誰が見えるようになるか**（新しい入口は増えるか。無認証にするなら理由を書く。外に出る経路なら公開経路の台帳へ追記するまでが完了条件）
2. **個人情報がどこに増えるか**（新しい保管場所・複製・ログ・外部送信が増えるなら、**削除手段と保存期限もこの時点で決める**）
3. **記録は残るか**（誰がその操作をしたかを事後に特定できるか。自動ワーカーや共有アカウントで実行されるなら「特定できない」と正直に書く）

### step2. 既知手法の照合

- 症状で**既存の解法カタログを引く**（`../../docs/institutions/pattern-catalog.md`）
- この問題類型に対する既知の手法・業界標準を**2つ以上**挙げる
- それぞれに**採用/棄却の理由を1行**。**棄却理由は必ず制約との衝突で語る**（好みで捨てない）
- 完全一致が無ければ「改造」か「組み合わせ」かを明示する

### step3. 複数案とトレードオフ

- 案は**最低2つ**。ラベルは **α β γ**
- **裸の二択は禁止**＝**分かれる理由（分岐軸）を先に実測・明示してから**並べる
- 各案に **得るもの / 失うもの / 可逆か不可逆か**（one-way door 判定）
- **推奨案を1つ選び、推奨理由を1行**書く。メニューを並べて終わらない

### step4. 全体図の提示（**文章 ＋ 図1枚の2点セット**）

- 詳細より先に地図を出す: スコープの範囲（**何が入り、何が入らないか**）・既存資産との接続点・分岐軸
- **片方だけは提示未完了**として扱う

### step5. 記録（採らなかった案を残す）

形式は **ADR**（文脈 → 選択肢 → 決定 → 帰結）。**採らなかった案と棄却理由を必ず残す**。将来「なぜこうなっている?」に答えられる状態が完成条件。

## 禁止事項

- 手法を1つだけ挙げて即適用（step2 を飛ばした証拠）
- 「α と β どちらにしますか」で終わる（分岐軸なき二択）
- 全体図なしで詳細から書き始める
- 教育・報告・運用など「ソフトウェア以外の設計」での適用免除

## 完成条件

提案を受けた側が、追加質問なしで次の3問に答えを持っている状態。①なぜこの案か ②他に何を検討して、なぜ捨てたか ③これはどこまでのスコープか。
