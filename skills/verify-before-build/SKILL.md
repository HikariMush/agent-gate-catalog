# verify-before-build — 根拠に基づく実装

対訳: **spec-driven development / context grounding ＋ design review with red team**。世界の spec-driven development が「リポジトリ内の証拠」で接地するのに対し、この型は**外部の権威**（公式仕様・法令・PDF）で接地する。

## 適用条件

- 実装の正しさが外部の権威に依存し、モデルの知識だけでは検証できない
- 間違えたときの実害が大きい（本番影響・法的リスク・利用者の実害）
- 単なるコードレビュー・バグ修正には使わない。**設計段階の思い込みを実装前に潰すためのもの**

## 鉄則

1. **一次資料を実際に取得する。記憶で設計しない** — 検索で概要を掴んだら、必ず実物（PDF・公式ドキュメント・実際の API レスポンス）を読む。「〜のはず」を一次資料からの引用に置き換える。PDF がバイナリのまま読めない場合も諦めず、確実にテキスト抽出する
2. **サンプルサイズを疑う** — 1件だけ見て構造を確定させない。複数サンプルを突き合わせ、「サンプル間で安定している部分」と「1件では分からなかった変動部分」を分けて報告する
3. **設計案は実装前に提示し、明示的な GO を待つ**
4. **敵対監査を必ず挟む** — 自己レビューで済ませない。独立した人格に「この設計を疑え・実データで殴れ」と発注する。監査側には前提（見た一次資料・件数・出典）を明示し、「n=1 で決めつけていないか」を明示的な攻撃観点として与える
5. **監査指摘は全部反映する。都合の良い所だけ拾わない** — 致命/中/軽微すべてを設計に織り込む。監査が「ここは合っていた」と認めた部分も記録し、無駄な手戻りを避ける
6. **実装前に既存資産を確認する** — 車輪の再発明と後退を避けるため、似た機能が既にないか探してから新規に書く。**この確認は敵対監査の中で行わせてもよい**
7. **実装の発注文に確定事実を全部埋め込む** — 実装担当が再調査・再判断せずに済むよう、一次資料からの確定事実・監査による修正点・既存資産の再利用方針を発注文に直接書く

## 工程

1. **調査**: 概要を検索 → 一次資料を取得。実際の引用付きで構造をまとめる（推測を混ぜない）
2. **設計案の提示**: 調査結果に基づく設計を簡潔に提示し、実装せず明示的な GO を待つ
3. **敵対監査の発注**: 前提（見たサンプル数・出典）を明示し、攻撃観点を番号付きで与える。**読み取り専用**（実装・修正はさせない）
4. **改訂**: 致命/中の指摘を全部反映した改訂版を作る。再度 GO を待つ
5. **既存資産の確認**: 流用できる既存機能・データがないか探す
6. **実装発注**: 確定事実・監査修正・既存資産の再利用方針・**新規に作る内容の自己監査ゲート**・検証コマンド一式を1つの発注文に埋め込む
7. **検証**: 検証コマンドの実出力を報告に貼らせる。実出力のない「完了しました」は無効

## 冷たい発注の型（履歴を共有しない相手に投げる場合）

```
あなたは verify-before-build の [調査|敵対監査|実装] 担当。同スキルの鉄則・工程に従うこと。
対象: <実装したい機能>
権威の所在: <一次資料の入手元・確認すべき仕様書>
実害: <間違えたときに何が起きるか。緊急度>
[監査担当] 監査対象の設計案とその根拠(一次資料・件数): <設計案を貼る>
[実装担当] 確定事実 / 既存資産 / 新規内容の自己監査ゲート / 検証コマンド
```

## 実例（この型が生まれた場面）

ある試験の実技モードの設計で、取得した PDF がバイナリ化して読めず、抽出ツールでテキスト化した。n=1 で立てた設計を敵対監査に掛けたところ n=3 に拡張され、「この形式は4パターン」という当初の想定が**3回中2回で0点になる**と判明した。さらに監査が既存の再利用可能なコードを発見し、当初設計より広い実装に修正された。

## スコープ外

コードの正しさだけを見る通常のレビュー / 既存アプリの体験監査 / 一次資料が存在しない純粋な設計判断（その場合は通常の red team 相談で足りる）
