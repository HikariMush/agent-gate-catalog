# ui-kihon — 画面を作るときの土台

対訳: **Nielsen のユーザビリティ10原則 ＋ Laws of UX（Hick, Fitts, Miller, Jakob, Postel, Tesler, Peak-End, Von Restorff）＋ heuristic evaluation**。

前提: この型は装飾の話ではない。**装飾で救えるのは設計の失敗のうち1割**。残り9割は「画面の目的が2つ以上ある」「状態が見えない」「入力を人間に押しつけている」で決まる。

## 工程1. 画面の宣言（コードを書く前に必ず埋める）

```
画面名:
利用者: <誰。「ユーザー」ではなく具体的な状態の人>
到達状況: <どこから来た。直前に何をした。何を期待している>
この画面の仕事: <1つだけ動詞で。2つ書きたくなったら画面を分ける>
成功: <利用者が何をしたらこの画面は成功か。1行>
離脱の原因(想定): <この画面で人が閉じるとしたら理由は何か>
主行動: <画面で一番大きく置くボタン1つ>
```

**「この画面の仕事」が2つ以上になったら画面を割る。** 主行動が決まらない画面は設計が終わっていない。

## 工程1b. 視線動線

各工程の操作中に見る情報を列挙し、その工程ブロックの視線範囲内に同梱できるかを1行ずつ書く。**参照のためのスクロール往復を設計で作らない**。同梱の手段は原本の移設か読み取り写しで、安易な複製で二重管理を作らない。

## 工程1c. 操作要素の単位設計（**飛ばしたら不合格**）

画面全体の宣言だけでは足りない。**画面に置く操作要素を1つ残らず列挙し、1つずつ次の表を埋める。**

| ラベル | どういう場面で押すか | 押すと何が起きるか | 直後に画面がどう変わるか | 失敗したら何が見えるか | 出る条件 |
|---|---|---|---|---|---|

- **「どういう場面で押すか」が書けない要素は削除する**（「あると便利そう」は利用者にとって毎回の判断コスト）
- **「直後に画面がどう変わるか」が「何も変わらない」なら不合格**
- **「失敗したら何が見えるか」が「何も出ない」なら不合格**（無言の失敗は最悪の体験）
- 既存画面の改善時も同じ。**まず全操作要素を棚卸しして表にする**

この工程が生まれた指摘: 「設計でボタン単位で見ていかないと体験は改善されない。これは大事故だ」。

## 工程1d. 配置と美しさの敵対監査

表が埋まったら配置を1枚の図に起こし、敵対的に攻撃する。**自分の設計に自分で合格を出さない**（別の人格に攻撃させる）。

配置: 主行動が視線の終点にあるか / 危険な操作が主行動の隣にないか / 頻度の高い操作ほど近く大きいか / 同種の操作が同じ場所に集まっているか / 押す順序と並び順が一致しているか。

美しさ（装飾ではなく**構造の秩序**として）: 視覚的な重さの序列が重要度の序列と一致しているか / 余白のリズムが揃っているか / 整列軸が通っているか / 色と形の語彙が最小か / 密度が均一すぎないか。

各指摘は「症状 → 違反している原則名 → 直し方」の3点で書く。

## 工程2. 原則を当てる（該当するものだけ）

| 原則 | 実装での意味 |
|---|---|
| ヒックの法則 | 選択肢は減らす・段階に割る・既定値を置く |
| フィッツの法則 | 主行動は大きく近く。危険な操作は逆に小さく遠く |
| ミラーの法則 / 認知負荷 | 1画面1目的・関連する項目をまとめる |
| ヤコブの法則 | 独自発明より慣習。戻る・保存・閉じるの位置を変えない |
| 状態の可視性 | 保存した / 送った / 処理中 / エラーを必ず出す |
| エラー予防 | 入力の形を限定する・不可逆操作は確認を挟む |
| 認識 > 記憶 | 前回値・候補・履歴を出す。識別子を暗記させない |
| ポステルの法則 | 全角/半角・空白・記号の揺れを受け入れて正規化する |
| ピークエンドの法則 | 完了画面を雑にしない。終わりに次の一手を置く |
| フォン・レストルフ効果 | 強調は画面に1つ |
| テスラーの法則 | 複雑さの総量は保存される。**利用者に押しつけず作り手が飲む** |

## 工程3. 実装の型（毎回見る6つ）

1. 主行動が1つだけ大きい 2. **空の状態を作る**（0件の画面＋次の一手のボタン）3. すべての操作に結果を返す 4. 入力は人間に優しく（空白除去・揺れ吸収・入力形式の指定）5. 不可逆な操作は二重にする 6. 触れる大きさ（タップ対象は最低44px相当）

## 工程4. 検品チェックリスト（実画面を見て付ける・推測で付けない）

**目的と導線**: 仕事が1つに絞れている / 主行動が3秒で分かる / 行き止まりがない
**状態**: 空の状態がある / 操作の結果が画面に出る / 読み込み中が分かる / エラー文が「何が起きたか＋どうすればいいか」になっている
**入力**: 必須と任意が分かる / 形式が示されている / 空白と全角半角を勝手に直している / **表示だけの重要な値がコピーできる** / 適切なキーボードが出る
**事故防止**: 不可逆操作に確認がある / 危険な操作が主行動の隣にない / 二重送信で壊れない
**見え方**: スマホ幅で崩れない / 強調が画面に1つ / 情報がグループになっている / 文字が小さすぎない
**言葉**: 利用者の言葉になっている / ボタンが動詞になっている / 否定形を使っていない

## 工程5. 実機で歩く（推測での合格を禁止）

実ブラウザでスマホ幅のスクリーンショットを撮り、**画像を見て**チェックリストを付ける。コードを読んで「たぶん大丈夫」で丸を付けることを禁止する。

## やってはいけない

画面に仕事を2つ以上持たせる / 空の状態を後回しにする / 表示専用テキストで重要な値を出す / 確認ダイアログを万能薬にする / 利用者に正規化させる / 強調を増やす / 「エラーが発生しました」 / **画面単位でしか設計を見ない**（操作要素の単位で場面と挙動を持たない設計は、あとから装飾でも改善でも救えない）

## 完了条件

工程1の宣言が全項目埋まっている / **工程1c の表が全操作要素分埋まっている** / **工程1d の敵対監査を別の目が実施した** / 工程4を**実画面のスクリーンショットを見て**付けた / 直した点を「症状 → 原則名 → 直し方」で記録した。
