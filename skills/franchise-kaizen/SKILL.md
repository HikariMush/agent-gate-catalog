# franchise-kaizen — 旗艦深掘り → マニュアル化 → 全店展開

対訳: **Yokoten（横展開・Toyota。そのまま複製せず copy-and-improve し、改善を新しい標準の下限にする）＋ pilot / lighthouse site → rollout ＋ playbook**。

目的: N 個の類似アプリを個別に浅くレビューするのではなく、旗艦1つに監査を集中し、問題を「発見手法・解決手法・検収手法」に抽象化して、マニュアルとして全店に展開する。監査が使い捨てではなく恒久資産に変わり、**N+1 店目（未来の新アプリ）にもそのまま効く**。

## 適用条件

- 同一エンジン/テンプレのコピーで作られたアプリ群がある
- 単発アプリなら、この型ではなく敵対監査や体験監査を直接使う
- エンジンを共有しない類似アプリ群なら、移植のトラックを省いてマニュアル適用のトラックだけで回す

## 鉄則（違反したら改善が無効）

1. **監査は旗艦1つに集中** — N 店に薄く撒かない。旗艦の選定基準（優先順）: ①実利用データがある ②コンテンツが最も厚い ③全機能が実戦投入済み。同一エンジンなら旗艦の深掘りがエンジン全体の深掘りになる
2. **新機能は展開前に旗艦で監査を通す** — 順序は 実装 → 監査 → 即修正 → マニュアル化 → 展開
3. **展開は二重トラック** — (a) エンジン移植（共有コードの変更を各店の固有設定に適合させる）(b) **マニュアルの発見手法を各店で再実行**して店舗固有の問題を拾う。**(a) だけの展開は失格**（旗艦に無い問題を素通しする）
4. **実装者 ≠ 検収者** — 各店の検収は移植をやっていない人格が行う。完了の定義は検証コマンド＋実出力
5. **還流で締める** — 店舗で見つかった一般化可能な問題はマニュアルへ、アプリ群を超えて効く原則は `PRINCIPLES.md` へ書き戻す。**還流のない展開は資産が育たず半分無駄**
6. **実データを監査官にする** — 利用ログが取れるなら必ず読む。機能の生死（使われていない機能）や設計のズレ（誤操作の痕跡）はコードレビューでは出ない

## 工程

1. **旗艦実装** — 既知のバックログを旗艦に実装。テスト＋再起動＋実打鍵の実出力まで。バックアップを最初に取る
2. **深掘り監査（旗艦のみ・並列）** — ①体験監査（憑依型ウォークスルー）②コード/データ監査（粗・セキュリティ・堅牢性・ロジックの設計・データ成長）③**到達経路監査**: 「このアプリ自身」だけでなく「このコンテンツを他に配信している面」を列挙して個別に確認する（統合ポータル・検索エンジンのキャッシュ・旧ブックマーク・掲載ページ）。**この監査が無かったため、同一店で同じ劣化ビューアの問題が2回別々に発見された**。「一次配信元だけ直して満足しない」が鉄則
   - 業務ロジック（判定・スコアリング等、**間違えると誤った判定を配布する**変更）は、実装の前に `verify-before-build` を通す
3. **即修正** — 小さいものは旗艦で即修正。大きいものはロードマップへ登録して今回は見送りを宣言する
4. **マニュアル化** — 1問題パターン ＝ 1エントリ。パターン名（具体動作で命名・造語禁止）/ 症状 / **発見手法**（別の店で同じ問題を再発見する具体手順。コピペ実行可能な粒度）/ 解決手法 / **検収手法**（直ったことを証明するコマンドと期待出力）/ 旗艦での具体例 / 適用条件
5. **展開（店舗ごとに並列）** — エンジン移植（固有設定に適合）＋ 発見手法の全再実行 ＋ ヒット修正 ＋ テスト ＋ 実打鍵
6. **検収（店舗ごとに独立）** — 独立検収官がマニュアルの検収手法と、無作為抽出したパターンの発見手法の再実行で合否を出す
7. **還流** — 一般化可能なものはマニュアルへ、アプリ群を超える原則は `PRINCIPLES.md` へ、大物はロードマップへ

## モデル配役（知能の置き場所）

この方法論の核は「**知能をマニュアルに前借りさせ、実行は安いモデルで回せる状態を作る**」こと。

- 旗艦実装・深掘り監査・マニュアル化 = **最上位**
- 展開・検収 = **中位で可**。ただし条件つきで、移植の正本とマニュアル（発見/解決/検収手法）が揃っている場合のみ。揃っていなければ中位に投げてはいけない（マニュアル無しの展開は旗艦知能の再発明になり高くつく）
- 還流 = 上位推奨（一般化の質がマニュアルの資産価値を決める）
- **マニュアルの合格基準 = 「中位モデルがこの文書“だけ”で発見→修正→検収を再現できる粒度」**

## 障害復旧

工程の生存条件は「**正本ファイルが書かれていること**」。移植の正本とマニュアルさえ残っていれば、任意のモデル・任意のセッションから展開を再開できる。実装担当には変更記録を**作業と同時に**書かせる（最後にまとめて書かせない — 途中で落ちると全損する）。

## スコープ外（**新規開店時は別ゲートとして必ず埋める**）

アプリ群をまたぐ大規模な再設計 / コンテンツの事実正確性監査 / 単発アプリの改善。**「エンジンが完璧に移植された」は「公開してよい」の証明にならない。** この型の検収はエンジンと UI の同一性しか見ない。事実監査とコンテンツ量の十分性を省いて公開したことが実際に2回問題化した。新規開店のチェックリストに独立項目として明記すること。
