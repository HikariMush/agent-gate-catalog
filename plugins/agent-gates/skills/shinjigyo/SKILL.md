# shinjigyo — アイデアから収益までの一本道

> **この手順は自前の台帳・検査スクリプトを前提とする。** 同梱していないので、無い場合は同じ項目を手動で確認する（何を確認すべきかは各手順に書いてある）。

対訳: **Stage-Gate（Cooper・段と gate で go / kill / hold / recycle を判定）＋ customer discovery / lean startup**。

差分は1点。**gate を通過した後に自律の度合いが上がる**（世界の Stage-Gate は人の会議体が gate を握り続ける）。人が握るのは**外向き送信 / 公開・本番反映 / お金**の3種だけで、それ以外は「進める」と宣言して連続実行する。

## 発動時の分岐

1. 登録済み事業の台帳を読む
2. 話題が**登録済みの事業**なら → その事業の監査スクリプトを実行し、出力を貼ってから正本の「現在地と直近の一手」で再開する。**監査なしで現状を語ることを禁止する**
3. **新しいアイデア**なら → 段A から開始する

## 工程（段の順番は一本道。各段の中身は「仮説 → 最小検証 → 修正」のループ。机上で全段詰め切ってから走らない）

- **段A アイデア出し** — 候補を α β γ… で複数案（悩み起点・手持ち資産起点・市場起点の3方向から）。選定基準 = 手持ち資産と接続するか / 週の帯域で回るか / 利益構造が説明できるか
  - **ドメイン降下スキャン**: 具体業種を1つ指定して降りる。①業種選定 → ②業務の列挙 → ③業務フロー分解 → ④軋轢の抽出（二重入力・手戻り・待ち・怖れ。**web 証拠のURL必須**）→ ⑤ボトルネック特定 → ⑥**金額換算**（その痛みは年間いくらの損か）→ ⑦**決裁者判定**（財布は誰か。**使う人と払う人が別人ならその翻訳が商品の一部**）→ ⑧**支払い構造**（予算枠の実在・既に払っている支出の付け替え・代替手段の価格アンカー・3壁＝専門性/面倒/怖さ）→ ⑨実装容易性 → ⑩営業容易性（決裁者への到達経路の実在・デモ可能性・1文で説明が通るか）→ ⑪横展開性 → ⑫**地雷チェック**（資格法域・要配慮個人情報・安全責任）→ ⑬検証の最小手 ＋ S/A/B/C 判定。全段に「確率的 / web 証拠あり」のラベルを付ける
  - **機能転植スキャン（ボトムアップ）**: 手持ちの動く機能から空白業種へ登る。①機能の棚卸しと抽象化（業種語彙を剥がす）→ ②本場特定（その機能が成熟している業種）→ ③空白業種の探索 → ④**空白の理由判定（肝・敵対必須）**: (a) 小さすぎて大手が作らない (b) ニーズが実は無い (c) 既存の道具で足りている (d) 規制・商習慣の壁 — **(a) と判定できた空白だけ先へ進む。空白＝チャンスと即断したら失格** → ⑤転植コスト判定 → ⑥以降は降下スキャンの⑥〜⑬に合流
  - **突合（交差判定）**: 縦軸＝降下スキャンで実在証明された痛み、横軸＝転植スキャンの手持ち機能。**交差したマスは「痛みの証拠＋デモ」が同時に揃っており検証の最小手が最短**＝候補の最上位
- **段0 目的の定義** — 収入目標・週の実働時間・位置づけ。本人にしか決められないので、想定解つきで聞いて裁定を取る
- **段1 顧客とボトルネック特定** — 誰の・どの悩みか。「顔の見える最初の顧客候補を実名で3人」が合格線
- **段2 商品と価格** — 成果物＋価格＋納期のパッケージに固める。都度見積だけの商売にしない
- **段3 実現可能性の一次判定（go/kill ゲート）** — 作れるか・売れるか・回るか、3つ全部に根拠を書く。加えて**評判軸チェック**（所属コミュニティに「金のためにやっている」印象を立てないか）。**判定が go なら、以降は外向き・公開・お金以外の裁定を待たず自律実行に切り替える**。kill なら理由と再挑戦条件を記録して止める（止める判断も成果）
- **段4 最小の売り物** — 「今日客が来ても受けられる」最小セット。この段で基盤を作る（専用ディレクトリ＋正本の事業フロー＋監査スクリプト＋自律キュー＋版管理＋台帳登録）
- **段5 収益試算** — 1件あたり粗利 × 獲得可能件数 ≧ 段0の目標、を数字で確認する。必要なリード数まで逆算する
- **段6 集客** — チャネルは同時に増やさない。1本ずつ「30日でリード何件」を計測して残すか捨てるか決める
- **段7 営業と契約** — リード → 相談 → 提案 → 見積 → 契約 → 着手金の型を固定する。書類を先に用意する
- **段8 納品体制** — スコープ膨張対策（含む/含まないの書面固定）。実装は委譲体制で本人の実働を最小化する
- **段9 維持と紹介** — 保守・フォロー・紹介依頼。新規獲得より既存維持が安い
- **段10 月次経営判断** — 見る数字は5つ以内。3ヶ月連続で試算を下回ったら修正か撤退を裁定する。冒頭で問いの正本を通してから数字を見る。締めに公理を蹴る1問（「この計画で誰も疑っていない前提は何か」）を**人間に**提示する（AI が自答してはいけない）

## 全段共通ルール（違反はミスではなく事故）

- **監査なしで現状を語らない**
- 判定は正本に書いた**数字基準**で行う。感想・印象で判定しない
- **ゲートは3種のみ**: 外向き送信 / 公開・本番反映 / お金。それ以外は「進める」と宣言して連続実行する
- 実装は委譲体制で。テスト全パス＋実起動確認なしに「完了」と言わない
- 一時サーバを立てさせる発注には「停止後にポート解放を確認した出力を貼る」を検証条件に必ず含める
- 人間への質問は想定解 α β γ… を複数並べて選ばせる形にする。持ち帰りは5分以内に割る
- **終了処理を毎回**: 正本の「現在地と直近の一手」更新 → コミット → 大きな前進があれば記憶の更新

## 想定監査（浅い想定の自己検出）

- 正本に書く数字には**出典か「未検証」マークを必ず付ける**。裏付けのない確率・転換率を裸で書いた時点で違反
- **段3の go 判定後・公開/課金の前・月次経営判断のとき**、設計に関与していない新鮮な目に敵対監査を発注する。成果物は「想定 / なぜ浅いか / 壊れ方 / 最小検証手」の4点セット
- 監査は**最上位の公理（何が本線か・資源配分の前提そのもの）も検査対象に含める**。実例: 「この事業が本線」を全セッションが無検証で継承し、監査の枠自体が公理の内側にあった。ニッチ人口 × 転換率で天井を測ったら、旗艦の器ではなかった

## 継続性ルール（自分がいなくなる前提で働く）

判断・状態・次の一手は必ずファイルに外部化する（**会話の中にしか無い状態＝作業未完了**）。終了処理は「次の担当（別モデル・別セッション・人間）への遺言」の品質で書く。節目ではバックアップを取る。キューに作業を積むときは、**実行者の権限で実行可能かを先に確認する**。
