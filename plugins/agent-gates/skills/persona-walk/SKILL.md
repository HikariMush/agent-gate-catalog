# persona-walk — 憑依型ウォークスルー監査

対訳: **cognitive walkthrough（Lewis, Polson, Wharton, Rieman 1990・CHI）＋ persona ＋ heuristic evaluation**。

差分は3つ。①ペルソナを**集客チャネル（来た導線）から設計する** ②**実ビューなしで語ることを禁止する** ③使うたびに原則が蓄積する。

目的: アプリを「作った人の目」ではなく「途中で閉じる普通の人の目」で歩き、心理と実画面の衝突点から改善項目を抽出する。具体（実画面・実文言・一人称の心理）と抽象（設計原則）を必ず往復する。

## 鉄則（違反したらウォーク無効）

1. **実ビューなしで語らない** — 実 HTML・実文言・実データを取ってから歩く。記憶や設計書から画面を再構成して語ることを禁止する。文言はすべて実物から引用する
2. **ペルソナは離脱しうる普通の人** — アプリに好意的な理想ユーザーを憑依対象にしない。暇つぶし・懐疑・時間がない・別目的、を混ぜる
3. **ペルソナは導線から設計する** — 集客チャネル（共有/検索/紹介/広告）ごとに1人。導線が違えば最初に見る画面も心理も違う
4. **各画面で「離脱するならここ」を必ず1つ以上言う** — 称賛だけのウォークは失格
5. **改善項目はファイルに外部化** — 会話内にしか無い指摘は未完了。台帳に重大度と実装コストをつけて書き出す

## 工程

### 1. ペルソナ定義（具体）

名前・年齢・職業・その瞬間の状況（信号待ち / 寝る前 / 昼休み）／**来た導線**（どこで URL を踏んだか。ここから最初に見る画面が決まる。トップとは限らない）／目的温度（暇つぶし何% / 軽い興味 / 明確な課題）／領域リテラシーと IT リテラシー／離脱の閾値。

### 2. 実ビュー取得（具体）

ペルソナが通る画面を導線の順に取得する。動的画面はレンダリング済みデータまで取る。クライアント側遷移が本丸のアプリは実ブラウザで通す。

### 3. ストーリーウォーク（具体⇄抽象の往復）

```
### 画面: <URL/状態>
**見えるもの（実ビュー）**: 実要素・実文言の引用
**心理（一人称）**: 「……」 ← ペルソナの内心
**衝突点**: 心理と画面のズレ（「なし」で流さない。無ければより意地悪な状況を想定し直す）
**抽象化**: 衝突点を原則に持ち上げる（「〜な人は〜する」形式）
**改善項目**: 原則から具体アクションに落とす（重大度＋実装コスト付き）
**離脱するならここ**: 最低1つ
```

### 4. 台帳化（抽象→具体）

改善項目を対象アプリ側の台帳に集約する。重大度は【離脱直結】>【体験低下】>【磨き】。実装コストは分単位で見積もる。優先度 = 重大度 × 導線の太さ ÷ コスト。1分で直る文言修正は「即直しリスト」として分離する。

### 5. 横断原則の蒸留（スキルの成長）

複数ペルソナ・複数画面から出た指摘を、**次のアプリに転用できる形の原則**に蒸留し、同ディレクトリの `PRINCIPLES.md` に追記する。アプリ固有名詞を消して書く。ウォーク開始時に必ず既存原則を読み、既知の原則違反の検出に使う（毎回ゼロから発見しない）。

## 並列実行の型

1人目はメインが自分で歩く（ストーリーの品質基準を見せる）。2人目以降は並列に投げてよい。発注時にこの SKILL.md を読ませ、書式と鉄則を守らせる。合流後、複数ペルソナが同じ場所で刺さった項目は重大度を1段上げる。

## スコープ外

改善の実装（台帳まで）／数値計測（ウォークは定性発見の道具）／ユーザーインタビューの代替ではない（仮説生成器であって検証器ではない）
