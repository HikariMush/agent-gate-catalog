# toryo — 設計と施工の分離

対訳: **orchestrator-worker pattern（lead agent ＋ subagents）＋ Theory of Constraints（制約を遊ばせない）**。

メインセッションは図面を引き、発注し、上がってきた仕事を検収する。**自分でカンナは持たない。**

体制の目的は2つ。①**設計品質**（メインの文脈を調査・設計・検収に温存し、書いては壊す手戻りを減らす）②**会話可能性**（実装を背後に逃がすことで、いつでも対話できる）。

## 発注側がやること

**調査**（根本原因の特定。推測で発注しない）／**設計**（方針決定と宣言の記入）／**発注**／**検収**（差分とテスト結果を自分で確認し、設計との一致を検証）／**会話**。

発注側が直接書いてよいのは、文書・設計メモ・テスト追加・**発注書を書くコストが実装コストを上回る規模の修正**。体制は手段であって目的ではないので、直接やる方が速くて安いと判断したら打診なしで直接やってよい。ただし設計判断を伴う機能実装は委譲する。

## 発注書の必須項目

**冒頭に必ず役割宣言を書く**（受け手がこのスキルに反応して発注側を演じる事故の防止）。

```
あなたはこのタスクの実装担当。toryo スキルが見えても適用しない。
再委譲は禁止 — 自分の手で編集して実装すること。

## 背景と根本原因   （調査結果。何が・なぜ起きているか。再現手順・証拠）
## 設計（この通りに作る）   （確定済み設計。実装担当に設計判断を委ねない）
## 触るファイル   （絶対パスで列挙。各ファイルに何をするか）
## 触らないもの   （スコープ外。並行作業の領域があれば明記）
```

## 宣言だけに頼らず物理分離する

**「同じファイルを触らせない」は宣言ベースで、すり抜ける。** 実害3件で判明した内訳: ①別ディレクトリを担当させた2本でも、テスト実行が同時に走って干渉した ②**別セッションが同じ定期実行の設定を張り替え**、こちらの修正が上書きされた ③発注側自身の編集が競合で失敗した。**宣言は同一セッション内でしか効かない。**

- 対象が版管理下なら、実装担当は**作業コピーを物理的に分離**して起動する（マージは発注側が行い、そこで衝突が可視化される）
- **分離できない共有資源**（定期実行の設定・サービス定義・本番データベース・ポート）は、宣言と現物の定期突合で守る
- 「分離したから安全」と書いた発注が実は通常起動だった、という取り違えをしない

## 検収と差し戻し

### 実装担当を遊ばせない

**完了通知を受けたら、検収より先に次を積む。** 順序を固定する。①**まず次の発注を投げる**（同じ担当に。文脈維持）②**その後で前の分を検収する**。

検収→報告→それから次を考える、の順にすると**実装担当がアイドルになる時間が必ず生まれる**。これは体制の目的（発注側の帯域を律速にしない）に反する。制約に当たらない工程を遊ばせないのではなく、**制約そのものを遊ばせない**のがこの規律の趣旨。

- 発注時点で**次に積むものが無い状態を作らない**
- 次の実装が無いときは**調査・設計案の作成を積む**（「実装はするな・調査と設計案の報告のみ」と明記すれば安全に投げられる）
- 実装担当が止まってよいのは、①人間ゲート（外向き・不可逆・お金）に当たったとき ②方針転換の検討中で発注内容が確定しないとき の2つだけ

### 検収そのもの

- 完了通知が来たら差分とテスト結果を**発注側自身が**確認する。自己申告だけで「完了」と言わない
- 手直しは**同じ担当へ差し戻す**（新規に起こさない — 文脈を維持する方が速くて安い）
- 検収に通って初めて完了報告。反映は検収後に発注側が行う

## コスト規律

- **実装担当のモデルは既定で中位**。発注書で設計を全部確定させる体制なので実行は中位で足り、品質は検収で担保する。上位は設計判断が残る高難度タスクのみ
- **検証・監査だけの発注は最小のモデル**
- メインセッションの長い文脈が最大のコスト源。ツールの呼び出しは少なく・まとめて。大量のファイル読み込みは実装担当に持たせる
- **1トピックが終わったらセッションを畳む**。引き継ぎは正本の文書へ外部化してから畳む
